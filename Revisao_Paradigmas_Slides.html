Inteiros: o tamanho é decisão de projeto
O que acontece quando o valor passa do limite?
§6.2.1.1, p. 236-237
IDEIA
  • Com sinal, em complemento de dois: n bits vão de −2ⁿ⁻¹ até 2ⁿ⁻¹−1 (int: −2.147.483.648 a 2.147.483.647).
  • Java e C dão a volta em silêncio; Rust deixa o programador escolher; Python não tem estouro.
  • Sem sinal (unsigned): C, C++, C#, Go e Rust têm; Java não tem.
Caso realEm 2014, o contador do vídeo “Gangnam Style” passou de 2.147.483.647 e o YouTube migrou para 64 bits. Em 1996, o Ariane 5 explodiu por um float de 64 bits convertido para inteiro de 16 bits.
CÓDIGO
// Java: dá a volta, sem aviso
int x = Integer.MAX_VALUE;
System.out.println(x + 1);        // -2147483648
Math.addExact(x, 1);              // ArithmeticException

// Rust: o programador escolhe
x.checked_add(1)      // None
x.wrapping_add(1)     // -2147483648
x.saturating_add(1)   // 2147483647

# Python: não existe estouro
print(2**100)   # 1267650600228229401496703205376
SEBESTA, 11. ed., §6.2.1.1, p. 236-237.

Fala sugerida

O tamanho do inteiro é parte do projeto da linguagem. Compare as três filosofias: silêncio (Java, C, Go), escolha explícita (Rust) e precisão ilimitada (Python).

Pontos que não podem faltar

  • Estouro silencioso é fonte de bugs graves: Ariane 5, contadores de 32 bits.
  • Math.addExact lança exceção; é a forma de 'ligar' a verificação em Java.
  • Python: int sem limite; JavaScript: Number é double, e BigInt para inteiros grandes.

06
Ponto flutuante e decimal
Dinheiro não é double
§6.2.1.2 e §6.2.1.4, p. 237-239
IDEIA
  • O IEEE 754 guarda número finito de bits: 0,1 é dízima em binário e não tem representação exata.
  • float (32 bits) ≈ 7 dígitos; double (64 bits) ≈ 15-16.
  • Nunca compare reais com ==: use tolerância.
  • Para dinheiro: tipo decimal (COBOL, C#, F#; BigDecimal, Decimal por biblioteca) ou centavos em inteiro.
Armadilhanew BigDecimal(0.1) herda o erro do double. Use a string: new BigDecimal("0.1").
CÓDIGO
// JavaScript: um único tipo numérico (double)
0.1 * 3 === 0.3                      // false
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON   // true
2 ** 53 + 1      // 9007199254740992  (perdeu 1)
2n ** 53n + 1n   // 9007199254740993n (BigInt)

// Java: decimal exato
new BigDecimal("0.1").add(new BigDecimal("0.2"))   // 0.3
new BigDecimal(0.1)   // 0.1000000000000000055511...
SEBESTA, 11. ed., §6.2.1.2 e §6.2.1.4, p. 237-239.

Fala sugerida

O erro não é do JavaScript: todas as linguagens que seguem IEEE 754 têm o mesmo comportamento. Pergunte: 'em Python, 0.1 + 0.2 dá o quê?' (0.30000000000000004).

Pontos que não podem faltar

  • Causa: representação binária finita de uma dízima.
  • Solução: decimal ou centavos em inteiro.
  • Caso real: míssil Patriot (1991), 0,1 s truncado em 24 bits, 0,34 s de atraso após 100 h.

Quem confere os limites?
§6.3 e §6.5, p. 240-255
IDEIA
  • Cadeia: tipo primitivo ou matriz de caracteres? Tamanho estático ou dinâmico? Mutável ou imutável?

Ponteiros e referências
O que dá errado e como as linguagens evitam
§6.11, p. 273-285
PROBLEMAS (Sebesta, p. 275-277)
  • Ponteiro solto (dangling): aponta para memória que já foi liberada (ou saiu de escopo). Usar é comportamento indefinido.
  • Variável do monte perdida: foi alocada, mas ninguém mais a alcança: vazamento de memória.
  • Ponteiros permitem apelidos: liberar por um nome deixa o outro solto.
int *cria(void) {
    int local = 42;
    return &local;      // pilha que vai sumir
}
char *buf = malloc(100);
buf = NULL;             // bloco perdido: vazamento
COMO AS LINGUAGENS EVITAM
LinguagemMecanismo
Cmalloc / free manuais, aritmética de ponteiros
Javareferências + coleta de lixo; sem aritmética, sem free
Goponteiros sem aritmética + coleta de lixo; escape analysis torna return &local seguro
Rustposse e empréstimo: o compilador prova que não há ponteiro solto, sem coletor
SEBESTA, 11. ed., §6.11.3-6.11.7, p. 275-285.

Fala sugerida

Treine o vocabulário: ponteiro solto × variável do monte perdida. Depois a comparação: GC (Java/Go) × posse (Rust) × manual (C).

Pontos que não podem faltar

  • Solto = usar depois de liberar. Perdida = perder a referência sem liberar.
  • Coleta de lixo tira o free do programador; Rust move a verificação para a compilação.
  • Hoare chamou os ponteiros de 'um passo para trás' (p. 280).

null e uniões discriminadas
O erro de um bilhão de dólares
§6.10 e §6.11, p. 270-280
IDEIA
  • União livre (C): os campos dividem a memória e nada diz qual está em uso: lixo ao ler o campo errado.
  • União discriminada (Rust enum, TypeScript, Java 21 sealed): uma etiqueta diz o tipo atual e o match é exaustivo.
  • null: Tony Hoare o chama de “erro de um bilhão de dólares”.
  • Option / Optional usam união discriminada no lugar de null: esquecer o caso None não compila.
CÓDIGO
// Rust: Option é uma união discriminada
fn buscar(id: u32) -> Option<String> {
    if id == 1 { Some("Ana".into()) } else { None }
}
match buscar(2) {
    Some(nome) => println!("{}", nome),
    None       => println!("não achei"),
}   // esquecer o None: erro de compilação

// Java: Optional
buscar(2).map(String::length).orElse(0);   // 0
SEBESTA, 11. ed., §6.10 e §6.11, p. 270-280.

Fala sugerida

Feche o bloco ligando duas ideias: 'união + etiqueta' dá segurança de tipos; 'Option' é o uso mais comum.

Pontos que não podem faltar

  • Livre = responsabilidade do programador; discriminada = compilador verifica.
  • Linguagens com tipos anuláveis checados: Kotlin (String?), TypeScript (strictNullChecks), C#, Swift.

Precedência, associatividade e efeitos colaterais
Em que ordem a expressão é avaliada?
§7.2, p. 300-309
IDEIA
  • Precedência: qual operador primeiro. Associatividade: o que fazer com operadores iguais (esquerda ou direita).
  • ** é associativo à direita: 2 ** 3 ** 2 = 512.
  • Na dúvida, use parênteses (p. 305).
  • Efeito colateral: a função altera algo além do valor devolvido. A ordem de avaliação dos operandos passa a importar.
Transparência referencialSem efeitos colaterais, f(x) + f(x) pode virar 2 * f(x). Conecta com o paradigma funcional (Aula 12).
CÓDIGO
# Python
print(-2 ** 2)       # -4   (** antes do menos unário)
print(2 ** 3 ** 2)   # 512  (direita para a esquerda)

// Java: a ordem é garantida (esquerda para direita)
System.out.println(1 + 2 + "3" + 4 + 5);   // 3345

/* C: ordem NÃO definida pelo padrão */
int a = 5;
int fun1(void) { a = 17; return 3; }
a = a + fun1();    /* 8 ou 20? */
SEBESTA, 11. ed., §7.2, p. 300-309.

Fala sugerida

Mostre que 'a + fun1()' pode dar 8 ou 20 conforme a linguagem: Java fixa a ordem (8), C e Go não definem (20 no gcc).

Pontos que não podem faltar

  • Associatividade à direita: **, ++, --, menos unário.
  • Efeitos colaterais + ordem não definida = resultado imprevisível.
  • O Excel faz =-2^2 dar 4: o menos unário vence ali.

Conversões e coerção
Quando a linguagem converte por você
§7.4, p. 310-313
IDEIA
  • Alargamento (int → long, int → double) costuma ser seguro; estreitamento perde informação e exige cast.
  • Coerção: conversão implícita. Esconde erros (p. 312).
  • Go e Rust exigem conversão explícita (float64(i), i as f64).
  • JavaScript e PHP convertem tipos em comparações: use === e !==.
Caso realNo PHP, "0e123" == "0e456" é verdadeiro: logins que comparavam hashes com == aceitavam senhas erradas.
CÓDIGO
// JavaScript
"5" - 2       // 3
"5" + 2       // "52"
true + 1      // 2
null + 1      // 1
undefined + 1 // NaN
0 == ""       // true
"" == "0"     // false
0 == "0"      // true   (não é transitivo!)
0 === "0"     // false  (=== não converte)

// Java
int grande = 123456789;
float f = grande;           // alargamento implícito
System.out.println((int) f);   // 123456792
System.out.println(1 / 2);     // 0 (divisão inteira)
SEBESTA, 11. ed., §7.4, p. 310-313.

Fala sugerida

Mostre o contraste: C/JS/PHP convertem; Go/Rust exigem explícito. A coerção torna o código mais curto e menos confiável.

Pontos que não podem faltar

  • == do JS não é transitivo: 0 == '' e 0 == '0', mas '' != '0'.
  • Divisão inteira em Java: 1/2 = 0 e 1/2.0 = 0.5.
  • Armadilha: acertos / total * 100 com inteiros dá 0.0.

Expressões booleanas e curto-circuito
Nem todo operando é avaliado
§7.5 e §7.6, p. 313-317
IDEIA
  • && e || fazem curto-circuito: param assim que o resultado é conhecido. & e | (bit a bit/booleanos) avaliam sempre os dois lados.
  • O curto-circuito protege acessos: i < n && v[i] != x não lê fora do vetor.
  • Cuidado: efeitos colaterais no 2º operando podem não ocorrer.
  • C, Python e JS aceitam qualquer valor no if (0, vazio e nulo são falsos); Java, Go e Rust exigem booleano.
CÓDIGO
// Java
String s = null;
s != null && s.length() > 0   // false
s != null &  s.length() > 0   // NullPointerException

// JavaScript: ?. e ??
const u = { nome: "Ana", endereco: null };
u.endereco?.cidade     // undefined, sem erro
const qtd = 0;
qtd || 10              // 10  (o 0 se perdeu!)
qtd ?? 10              // 0   (só troca null/undefined)

# Python: and/or devolvem um dos operandos
0 or "padrão"          # "padrão"
3 > 2 > 1              # True: (3>2) and (2>1)
SEBESTA, 11. ed., §7.5-7.6, p. 313-317.

Fala sugerida

Reforce o uso defensivo: verificar antes de acessar. Esse padrão é o mesmo da busca do livro (p. 316).

Pontos que não podem faltar

  • && evita NullPointerException e acesso fora do limite.
  • || com valor 0 é armadilha: use ?? em JS.
  • Em C, 3 > 2 > 1 é 0: (3>2)=1 e 1>1 é falso.

Seleção: else pendente e switch
Quando o fluxo 'cai' ou se perde
§8.2, p. 330-341
IDEIA
  • else pendente: em C, Java, C++ e C#, o else pertence ao if mais próximo sem else. A endentação é ignorada.
  • Chaves obrigatórias (Go, Rust, Perl) eliminam o problema.
  • switch do C: sem break, o controle cai (fall-through) para o caso seguinte.
  • Alternativas de projeto: Java 14 case X ->, Go (cada caso termina sozinho), C# (proíbe cair), Rust match (exaustivo).
CÓDIGO
/* C: sem break, o controle "cai" */
switch (index) {
  case 1:
  case 3: odd += 1;
  case 2:
  case 4: even += 1;
  default: printf("Error\n");
}  // index = 1: odd, even E erro!

// Java 14+: switch como expressão
String tipo = switch (dia) {
  case SAB, DOM -> "fim de semana";
  case SEG, TER, QUA, QUI, SEX -> "dia útil";
};

// Rust: match exaustivo
match n { i32::MIN..=-1 => "negativo", 0 => "zero",
          1..=9 => "um dígito", _ => "vários dígitos" }
SEBESTA, 11. ed., §8.2, p. 330-341.

Fala sugerida

O fio condutor: mecanismos que 'parecem certos' mas fazem outra coisa. Leve a turma a prever o que o switch de C imprime.

Pontos que não podem faltar

  • Fall-through é uma escolha de projeto herdada do C.
  • O else pendente ainda é causa de bug em C/Java; chaves resolvem.
  • match exaustivo: esquecer um caso é erro de compilação.

Laços, goto e comandos protegidos
Controle de fluxo e legibilidade
§8.3-8.5, p. 342-355
IDEIA
  • Böhm e Jacopini (1966): sequência, seleção e laço lógico bastam; goto não é necessário. Dijkstra (1968): “goto é prejudicial”.
  • break, continue e return são gotos restritos; Java tem break rotulado.
  • for ... in (JS) percorre chaves; for ... of percorre valores.
  • Comandos protegidos de Dijkstra: várias guardas verdadeiras → escolha não determinística (base do select de Go).
Casos reais“goto fail” (Apple, 2014): um goto fail; duplicado pulou a verificação do certificado. Zune (2008): laço while sem progresso no último dia do ano bissexto.
CÓDIGO
// JavaScript
const notas = [10, 20, 30];

IDEIA

Impasse (deadlock)
Espera circular por recursos
§13.2.1, p. 551
IDEIA
  • Impasse: duas ou mais tarefas ficam bloqueadas, cada uma esperando um recurso que a outra segura. O programa congela, sem erro.
  • Causa típica: espera circular por travas adquiridas em ordens diferentes.
  • Soluções: adquirir as travas sempre na mesma ordem; tryLock com tempo limite; trava única; passagem de mensagens.
  • Vivacidade (p. 551): garantia de que o programa continua progredindo.
Corrida × impasseCorrida corrompe dados em silêncio. Impasse trava o programa. Ferramentas diferentes: exclusão mútua resolve a corrida, mas mal usada causa impasse.
DIAGRAMA E CÓDIGO
// Java: ordens opostas -> impasse
synchronized (X) { pausa();
    synchronized (Y) { ... } }     // Tarefa A
synchronized (Y) { pausa();
    synchronized (X) { ... } }     // Tarefa B
SEBESTA, 11. ed., §13.2.1, p. 551.

Fala sugerida

Use o diagrama: A segura X e quer Y; B segura Y e quer X. Ninguém avança. Quebrar a espera circular é a solução clássica.

Pontos que não podem faltar

  • Impasse não gera erro: o programa simplesmente para.
  • Ordem global de aquisição quebra o ciclo.
  • tryLock/timeout detecta e desiste; mensagens evitam travas.

IDEIA

Scheme e Haskell em resumo
Notação prefixa, listas, recursão e padrões
§15.5 e §15.8, p. 641-671
SCHEME
  • Notação prefixa: (+ 3 7 10 2); sem precedência.
  • define vincula nome a valor (não é atribuição). Tudo é expressão: if e cond devolvem valores.
  • Listas: '(A B C); car = primeiro, cdr = o resto, cons = constrói.
  • Padrão de recursão: 1) lista vazia? 2) usa o car; 3) chama com o cdr.
  • Recursão em cauda vira iteração (Scheme exige): não cresce a pilha.
(car '(A B C))      ; A
(cdr '(A B C))      ; (B C)
(cons 'A '(B C))    ; (A B C)

(define (membro atm a_list)
  (cond ((null? a_list) #f)
        ((eq? atm (car a_list)) #t)
        (else (membro atm (cdr a_list)))))
HASKELL
  • Casamento de padrões, guardas (|) e inferência de tipos; puro.
  • Compreensão de listas: [n * n | n <- [1 .. 5]].
  • Currying: função de vários parâmetros é cadeia de funções de um; add5 = add 5.
  • Avaliação preguiçosa: calcula só quando precisa; permite listas infinitas.
